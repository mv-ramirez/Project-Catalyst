SharePoint RAG API — Handover Guide

Repo path: cf8/push/  ·  Written 2026-10-23 from the repository code, RAG_API_SPEC.md, the live OpenAPI spec and cf output. Contains no secrets — only variable names and where to find them.

Read this first. The service is deployed and running on SAP BTP Cloud Foundry. Day to day it needs almost nothing. The things that can hurt you are: the destructive /db/* endpoints (guarded by ENABLE_DESTRUCTIVE), the table-set switches BRAIN_READ_SET / BRAIN_WRITE_SET, and the HDI container shared with the Node db module (see §6).

1. Overview

A FastAPI service (api.py) that ingests documents from three sources — Microsoft SharePoint (MS Graph), SAP BTP Object Store (S3) and the local /tmp filesystem — extracts text, splits it into chunks, embeds each chunk with BAAI/bge-small-en-v1.5 (384-dim) and stores everything in SAP HANA Cloud. It then serves semantic search (cosine similarity, with metadata filters) for RAG use, over REST and over an MCP server for Claude Desktop.

The content is the "BTP-Brain" knowledge base: SAP delivery guidelines and deliverable templates, organised by layer, category and deliverable code.

Getting access

  1. Install the CF CLI, then cf login -a https://api.cf.ap10.hana.ondemand.com and choose the org/space above. You need Space Developer rights; ask the BTP subaccount admin.
  2. For API calls, send the key in the X-API-Key header. The key is the app's API_SECRET_KEY environment variable. Retrieve it with cf env sharepoint-rag-api (this prints secrets — do not paste the output anywhere). Hand it over via your team's password manager, not email.
  3. To rotate the key: POST /admin/generate-key returns a new random key. Set it with cf set-env sharepoint-rag-api API_SECRET_KEY <new> and put the old value in API_SECRET_KEY_OLD so existing clients keep working during the switch; then cf restage.

The runtime detects CF by the presence of VCAP_SERVICES. The container image holds no credentials; all three service bindings (HANA, Destination, Object Store) are injected at runtime.

Authentication & token flow (MS Graph)

EnvironmentSteps

  2. POST {url}/oauth/token (client credentials) → XSUAA bearer token.

The token is cached in a module-level variable behind a lock and refreshed 60 s before expiry, so no request waits on a token exchange. The same code path serves all environments.

Tag derivation from folder paths

Files carry tags used for filtered retrieval: layer, layer_category, deliverable_code, client_name, project, source. They are parsed from the path with the layout <BTP-Brain root>/<layer>/<Guidelines|Templates>/<deliverable>[/<client>]/file. The parsers are _flatten_item() (SharePoint) and _parse_s3_tags() (S3), which anchors on a root folder named knowledge-base or btp-brain. deliverable_code and client_name are set only for Templates folders. Folder names are typed by hand, so the deliverable is matched case-insensitively against the short name, the rowId or the full name.

5. Vectorization pipeline

  1. Input. SharePoint items via Graph (download with 3 retries, back-off 5/15/30 s, 429 Retry-After honoured), S3 objects, or local /tmp paths.
  2. Change detection. _filter_stale_items() compares SharePoint lastModifiedDateTime (truncated to seconds) with the value stored in the files table. Unchanged files are skipped; the response reports skipped_unchanged. If the DB map can't be read, everything is processed. Since 2026-10-07 the ingest also skips upserts for unchanged files, chunks and raw chunk records.
  3. Extraction. _extract_text(): docx/dotx (python-docx, now including table cells with an XML w:t fallback), doc (olefile), xlsx/xlsm (openpyxl), xls (xlrd 1.2.0), pdf (pdfplumber), pptx/pptm (python-pptx), rtf, msg, csv, json, xml/html, zip (recursive), and plain-text types (txt, md, py, js, ts, sql, yaml, ini, toml, log, cfg, java, cs, abap).
  4. Chunking. _semantic_chunks(text, max_tokens=512): splits on newlines and packs paragraphs until about 2,048 characters (token ≈ 4 chars). No overlap.
  5. Embedding. BAAI/bge-small-en-v1.5, normalised vectors, model cached under SENTENCE_TRANSFORMERS_HOME (/tmp/models). Loaded lazily on first use, so the first vectorize after a restart is slow.
  6. Upsert. db.ingest(): files table, text chunks, vectors; plus raw base64 download chunks (FILES_CHUNK), the file registry and SharePoint version history. Tags are written when the tag columns exist.
  7. Artifacts. An HTML run report and a per-call log are written under DOWNLOAD_PATH/<YYYYMMDD>/ and uploaded to S3. View them at /analysis and /analysis/latest.

With use_delta=true the first Graph call returns the whole drive, so items are filtered client-side by parentReference.path to avoid cross-folder contamination.

Pipeline detail

#StepDetail
1Fetch filesGraph /drives/{drive_id}/root/delta (or folder-scoped delta), following @odata.nextLink pages; each item is flattened to id, name, type, size, dates, web and download URLs.
2Fetch versionsPer file, /drives/{id}/items/{id}/versions, throttled (default 1 s between calls) to stay under Graph rate limits. Returns version id, size, modifier and download URL.
3Change detectionSee below.
4DownloadStreamed in 8 KB chunks, 300 s read timeout, 3 attempts, back-off 5 → 15 → 30 s, 429 Retry-After honoured.
5Extract textBy extension (table in the step list above).
6ChunkNewline-split paragraphs packed to ~2,048 characters; no overlap.
7Embedbge-small-en-v1.5, 384-dim, normalised; lazy-loaded and cached in /tmp/models.
8HANA upsertUPSERT … WITH PRIMARY KEY into the files, text-chunk and vector tables (vectors via TO_REAL_VECTOR()), plus raw chunks, registry and versions.
9Write outputsRecords appended one at a time to JSONL files under DOWNLOAD_PATH.
10Report & uploadHTML run report and call log uploaded to S3 runs/YYYYMMDD/; an upload failure is a warning, not a run failure.

Memory strategy. Only running counts are kept across the file loop. File bytes are freed after extraction, extracted text after chunking, and per-file chunk and vector lists after the upsert. This is what lets a large library fit in the 1,536 MB container.

Change-detection outcomes

db.get_modified_map() makes one query for every known item_id → stored last_modified. _filter_stale_items() truncates both timestamps to seconds before comparing:

CaseConditionResult
UnchangedTimestamps equalSkipped, counted in skipped_unchanged; no further I/O.
Newitem_id not in the mapFull download → extract → chunk → embed → upsert.
ModifiedTimestamps differRe-vectorized; existing rows overwritten through the primary-key upsert.
DB unreachableget_modified_map() raisesEverything is processed. Deliberate: re-doing work is safer than silently skipping.

The filter reads the files table's last_modified column, not FILE_REGISTRY. /tmp files are stored in the same files table with source='tmp'.

6. HANA tables & table sets

Two physical sets of the same seven tables exist because of the HDI migration:

KeyLegacy (CATALYSTPLATFORM_BRAIN_*)HDI (CATALYSTPLATFORM_TB_BRAIN_*)
sp_files…_BRAIN_SP_FILES…_TB_BRAIN_SP_FILES
s3_files…_BRAIN_S3_FILES…_TB_BRAIN_S3_FILES
text_chunks…_BRAIN_TEXT_CHUNKS…_TB_BRAIN_TEXT_CHUNKS
vectors…_BRAIN_VECTORS…_TB_BRAIN_VECTORS
files_chunk…_BRAIN_FILES_CHUNK…_TB_BRAIN_FILES_CHUNK
file_registry…_BRAIN_FILE_REGISTRY…_TB_BRAIN_FILE_REGISTRY
sp_versions…_BRAIN_SP_FILES_VERSIONS…_TB_BRAIN_SP_FILES_VERSIONS
  • Current production setting: BRAIN_READ_SET=hdi, BRAIN_WRITE_SET=hdi (from manifest.yml). The code default is legacy for both.
  • BRAIN_WRITE_SET=both dual-writes: the READ set is primary (a failure raises); the other set is best-effort (failure logged and returned under errors). Use GET /db/tables to compare counts before flipping the read set.
  • The HDI tables are owned by the Node db module in the BTP-Catalyst-Platform repo (db/src/*.hdbmigrationtable). Python never issues DDL against them. create_tables, migrate_tables and drop_tables refuse to run when HDI is active; a past incident (Sep 10) where Python created objects in a container HDI also owns caused data loss.
  • Renaming an HDI table is a two-repo change: the .hdbmigrationtable file and the constant in db.py must move in the same commit. Always use the constants, never inline a table name.
  • Vectors are 384-dim. Retrieval filters are applied before cosine ranking, so top_k counts only matching rows.

Table purposes

TableKeyHolds
SP_FILESitem_idOne row per file (all sources): name, type, size, URLs, last_modified, version count, source, tags (layer, layer_category, deliverable_code, …). Change detection reads this.
S3_FILESitem_idS3 object registry: key, ETag, storage class, timestamps.
TEXT_CHUNKSitem_id, chunk_idRaw chunk text (NCLOB), fetched after a vector hit.
VECTORSitem_id, chunk_idREAL_VECTOR(384), searched with COSINE_SIMILARITY(vector_data, TO_REAL_VECTOR(?)) inside HANA — no external vector store.
FILES_CHUNKper file / chunkRaw base64 download chunks for /rebuild. The largest table (~10.9 KB per row).
FILE_REGISTRYitem_id, sourceLightweight cross-source record (filename, modified time), written best-effort after ingest. Not what the change filter reads.
SP_FILES_VERSIONSitem_id, version_idSharePoint version history with size, modifier and download URL.

Vector wire format. hdbcli returns a vector column as a binary blob: [uint16 dims LE][uint16 pad][float32 × 384 LE] = 1,540 bytes. /db/vectors/{item_id} decodes it to plain floats. Per the original diagram notes, stored vectors matched locally recomputed embeddings (cosine 1.0).

Query flow (POST /db/query). text → encode to a 384-dim vector → COSINE_SIMILARITY join over the filtered candidates → top K → {item_id, filename, chunk_id, chunk_data, score}.

SharePoint path → tags (_flatten_item()): the folder path is split on /; index 2 = layer, 3 = layer_category, 4 = deliverable segment (matched against deliverables.json), 5 = client name (Templates only). Example: /BTP-Brain/Layer3/Templates/FDD/ClientX/…. The deliverables file has 19 entries across the phases discover, prepare, explore, realize, deploy and run.

Switching table sets (the safe order)

  1. Confirm the HDI tables exist: GET /db/tables.
  2. Set BRAIN_WRITE_SET=both; restage; run normal vectorize calls.
  3. Run POST /db/backfill (or python migrate_brain_data.py copy) for pre-existing rows, then verify.
  4. When counts match, set BRAIN_READ_SET=hdi; later narrow the write set.
  5. Don't drop the legacy tables until the HDI set has lived in production for a good while.

14. Known issues & open items

  • Chunking quality (from RAG_API_SPEC.md §11): token counts are character-approximate (chars/4); no overlap between chunks; no metadata inside chunks; embedding is not batched (one encode() call per chunk, slow on big runs); vectors are not stamped with model name or version, so a model change cannot be detected from the data. The earlier "chunk exceeds model window" gap is resolved.
  • Single instance, ephemeral disk. One CF instance with /tmp storage; run artifacts and the model cache vanish on restart (artifacts are mirrored to S3).
  • Auth is all-or-nothing. One shared API key (or none, if the variable is unset), CORS open to all origins, and the MCP routes use the same key.
  • Startup tolerance. If SharePoint init fails the app still starts and returns 503 on SharePoint routes until it recovers; check GET /health.
  • Two repos coupled. HDI table definitions live in BTP-Catalyst-Platform. Schema changes need changes in both.
