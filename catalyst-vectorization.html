1 — High-Level Architecture

What this slide shows: The end-to-end system topology of the Catalyst RAG platform. At the center is the FastAPI application (api.py + db.py + s3.py) deployed as a single Cloud Foundry app instance on SAP BTP with 1 536 MB RAM and 4 096 MB disk. To its left, SharePoint Online is the primary document source — files are fetched via the Microsoft Graph API using a drive delta endpoint that returns only changed items since the last run, keeping incremental syncs fast regardless of library size. To its right, SAP HANA Cloud stores all vectorized content in the BRAIN_* table family; every search query hits HANA's native COSINE_SIMILARITY() function directly inside the database engine, requiring no external vector store. Further right, S3 / Object Store receives run artifacts — HTML analysis reports and structured call logs — automatically uploaded after every vectorize cycle under a dated prefix. Below the main horizontal flow, three ingest sources are shown side-by-side: SharePoint (MS Graph item ID as the unique key), S3 / Object Store (ETag / MD5 as the key), and the CF container's /tmp filesystem (md5 of the absolute path as the key) — all three funnel into the same HANA tables through a shared pipeline, so source is transparent to the query layer. At the bottom, two infrastructure concerns are highlighted: the BTP Destination Service manages the OAuth2 credential chain (XSUAA → MS Graph token) so the app never handles long-lived secrets itself; and VCAP_SERVICES injects all three service bindings — HANA, Destination, and Object Store — into the container at CF runtime, meaning the Docker image contains zero credentials and is safe to store in any registry.

2 — Authentication & Token Flow

What this slide shows: The two authentication paths the application supports, and how each one delivers a live MS Graph Bearer token to the SharePoint download logic. On Cloud Foundry (production), the flow is a three-step chain: the app reads the BTP Destination Service binding from VCAP_SERVICES (clientid, clientsecret, url, uri), then POSTs to {url}/oauth/token using client credentials to obtain an XSUAA Bearer token, then GETs {uri}/destination-configuration/v1/destinations/BTP-CP_MS_Graph using that XSUAA token to retrieve the destination configuration. The Destination Service returns an authTokens[] array; the app extracts the first entry with type = bearer and a non-empty value field as the live MS Graph token. If no token is present in authTokens (e.g. the destination is not configured for token forwarding), the app falls back to calling Azure AD's /oauth2/v2.0/token endpoint directly using the tokenServiceURL, clientId, and clientSecret from the destination configuration. The resolved token is cached in a module-level variable with a thread-safe lock and proactively refreshed 60 seconds before its expiry time — so no request ever blocks on a token exchange mid-flight. For local development, credentials come from a .env file (TENANT_ID, CLIENT_ID, CLIENT_SECRET) or local JSON sidecar files, and the app authenticates directly against login.microsoftonline.com/{tenant}/oauth2/v2.0/token with scope https://graph.microsoft.com/.default, bypassing the BTP layer entirely. HANA credentials resolve from hana_creds.json or environment variables; S3 credentials from s3_creds.json or environment variables — the same code path handles all three environments without modification.

3 — Vectorization Pipeline (core flow)

What this slide shows: The complete 10-step vectorization pipeline that executes on every call to /vectorize, /vectorize/folder/{path}, /pipeline, or their S3 and /tmp equivalents. Step 1 — Fetch Files: calls the MS Graph /drives/{drive_id}/root/delta endpoint (or /folder:/delta for folder-scoped runs), paginating through all @odata.nextLink pages until the full item list is collected; each item is flattened into a metadata dict (id, name, type, size, dates, web URL, download URL). Step 2 — Fetch Versions: for each file, a separate Graph call to /drives/{id}/items/{id}/versions retrieves the full version history with configurable inter-request throttling (default 1 s delay) to avoid Graph API rate limiting; returns version_id, size, modified_by, and a pre-authenticated download URL per version. Step 3 — Change Detection: the full SharePoint item list is filtered against HANA's BRAIN_SP_FILES table — only files whose lastModifiedDateTime differs from the stored last_modified (or that are not yet in HANA) are queued for processing; unchanged files are counted in skipped_unchanged and skipped with zero further I/O. Step 4 — Download: file bytes are streamed in 8 KB chunks via the Graph BaseURL (pre-authenticated download link) with a 300 s read timeout, up to 3 retry attempts, and exponential backoff (5 s → 15 s → 30 s); 429 responses honour the Retry-After header. Step 5 — Text Extraction: routed by file extension — docx/doc via python-docx / olefile, xlsx/xls via openpyxl / xlrd (cell values joined with " | " per row), pdf via pdfplumber, pptx/ppt via python-pptx / olefile, eml/msg via the email stdlib and extract-msg, zip via recursive extraction. Step 6 — Semantic Chunking: splits on newlines into paragraphs, accumulates greedily until the window reaches 512 tokens (~2 048 chars), then starts a new chunk; no overlap currently (tracked in backlog). Step 7 — Embedding: each chunk is encoded by BAAI/bge-small-en-v1.5 with normalize_embeddings=True, producing a unit-norm 384-dimensional float32 vector; the model is lazy-loaded and cached in /tmp/models/ across requests. Step 8 — HANA Upsert: db.ingest() writes three table rows per chunk via UPSERT … WITH PRIMARY KEY — one row each in BRAIN_SP_FILES, BRAIN_TEXT_CHUNKS, and BRAIN_VECTORS (using TO_REAL_VECTOR() to convert the float list to HANA's native binary format); db.ingest_chunk_summary() writes/updates one row in BRAIN_FILES_CHUNK. Step 9 — Write Outputs: chunk text, vector data, and raw base64 file bytes are appended to separate JSONL files in /tmp one record at a time — the pipeline never holds all chunks or vectors in memory simultaneously, so it scales to arbitrarily large libraries within the CF dyno's 1 536 MB RAM budget. Step 10 — Report & Upload: a dark-theme HTML report is generated summarising vectorized count, chunk counts, skipped files, retry events, HANA table row counts, and output file sizes; both the report and the structured call log are uploaded to S3 under runs/YYYYMMDD/ as non-fatal background operations.

4 — Change Detection Detail

What this slide shows: The detailed mechanics of the change detection filter that prevents redundant re-vectorization. Before a single file is downloaded, db.get_modified_map() issues one query against BRAIN_SP_FILES (or the equivalent registry table for S3 / /tmp sources) to retrieve a Python dict mapping every known item_id to its stored last_modified timestamp string. Each item from the SharePoint item list is then evaluated against this map using _filter_stale_items(), which applies _norm_ts() to both timestamps — truncating fractional seconds — before comparing, to absorb the format differences between SharePoint's ISO 8601 strings and what was written by the previous run. The result is one of four outcomes: (1) UNCHANGED — timestamps match exactly after normalization; the file is appended to skipped_unchanged and no further I/O occurs for it in this run, not even a HANA read. (2) NEW — item_id is not present in the map at all, meaning HANA has never seen this file; it is queued for full download → extract → chunk → embed → upsert. (3) MODIFIED — item_id is known but the timestamp differs, meaning the file was edited in SharePoint after the last vectorize run; it is queued for re-vectorization and all existing chunk and vector rows for that item_id are overwritten atomically via UPSERT … WITH PRIMARY KEY — no orphaned stale chunks can exist. (4) DB UNREACHABLE — if get_modified_map() raises any exception (HANA connection failure, timeout, etc.), the filter falls back to processing every item in the list; this is intentional — it is safer to re-vectorize everything than to silently skip items whose change status cannot be determined. The right panel also shows how item_id is derived per ingest source: for SharePoint it is the MS Graph opaque string ID (e.g. 01HOEYRQ…), for S3 it is the object's ETag value (MD5 of content), and for /tmp files it is md5(abs_path) — stable across container restarts because the path does not change. All three are stored in the same PK column, making the UPSERT logic and query layer fully source-agnostic.

5 — SAP HANA Database Schema (BRAIN_* Tables)

What this slide shows: The complete schema of the seven HANA Cloud tables that back the RAG platform, all managed by the HDI container and prefixed under schema BTP_CATALYST_PLATFORM_HDI_BTP_CATALYST_PLATFORM_DB_DEPLOYER_1. BRAIN_SP_FILES is the SharePoint file registry — one row per file, keyed by item_id (MS Graph opaque ID). It stores filename, file type, extension, size in both human-readable and byte forms, the SharePoint web URL, the document path, the last-modified and created-by/modified-by timestamps, version count, and the ingest source flag. Three derived classification columns — layer, layer_category, and deliverable_code — are populated by _flatten_item() in api.py by splitting the SharePoint folder path on "/" and matching the segment at index 4 case-insensitively against a 15-entry deliverables.json lookup loaded at startup. BRAIN_TEXT_CHUNKS stores the raw extracted text per chunk as an NCLOB — one row per (item_id, chunk_id) pair — and is the table fetched by /db/chunks/{item_id} to return chunk text after a vector search identifies the relevant chunk IDs. BRAIN_VECTORS stores the 384-dimensional embeddings using HANA's native REAL_VECTOR(384) column type. Vectors are written via TO_REAL_VECTOR(?) from a JSON float array and read back as a binary blob in the format [uint16 dims LE][uint16 padding][float32×384 LE] = 1 540 bytes; the /db/vectors/{item_id} endpoint decodes this binary representation and returns plain float arrays, which have been validated to be byte-for-byte identical to locally re-computed embeddings (cosine similarity = 1.0). At query time, HANA evaluates COSINE_SIMILARITY(vector_data, TO_REAL_VECTOR(?)) inside the engine for maximum performance. BRAIN_FILES_VERSIONS stores the full SharePoint version history per file — one row per (item_id, version_id) — capturing size, modified timestamp, modifier identity, and the pre-authenticated download URL for each version. BRAIN_FILES_CHUNK is a summary table with one row per file recording only the total chunk count, used by the analysis report. BRAIN_S3_FILES mirrors the SP file registry for S3-sourced objects, storing the S3 key, ETag, storage class, and timestamps. BRAIN_FILE_REGISTRY is a lightweight cross-source change-detection table keyed by (item_id, source) that records only filename and modified_datetime — its purpose is to back the incremental detection logic without requiring a full BRAIN_SP_FILES query for non-SharePoint sources.

6 — Output Files Written to /tmp (DOWNLOAD_PATH)

What this slide shows: Every file the pipeline writes to /tmp (the CF container's ephemeral DOWNLOAD_PATH) during a vectorization run, organized by ingest source. SharePoint outputs (sp_*): sp_chunks_<ts>.jsonl — one JSON object per line, each containing item_id, chunk_id, chunk_data (raw extracted text), and filename; sp_vectors_<ts>.jsonl — one object per line with item_id, chunk_id, vector_id, and the 384-float vector_data array; sp_files_chunk_<ts>.jsonl — raw base64-encoded 8 KB download chunks per file, used by the /rebuild endpoint to reassemble the original file bytes on demand without hitting SharePoint again; sp_root_data_<ts>.json — the full flattened metadata array for every file fetched during the run; sp_files_versions_<ts>.json — version history for all root files; sp_analysis_<ts>.html — a self-contained dark-theme run report covering vectorized count, chunk totals, skipped files, retry events, HANA table row counts, and output file sizes; <endpoint>_<ts>.log — a structured per-call log capturing every download, extraction, chunk, upsert, and error event. S3 outputs (s3_*): s3_chunks_<ts>.jsonl, s3_vectors_<ts>.jsonl, s3_files_chunks_<ts>.json (8 KB base64 blocks per object), and s3_root_data_<ts>.json (S3 object metadata including ETag, storage class, and size). /tmp source outputs (tmp_*): tmp_chunks_<ts>.jsonl, tmp_vectors_<ts>.jsonl, tmp_files_chunks_<ts>.json, and tmp_root_data_<ts>.json with local file metadata (path, mtime, size). All JSONL files are written one record at a time using append mode — the pipeline never holds a full file's chunks or vectors in memory simultaneously. After every run, the HTML report and log are uploaded non-fatally to S3 under runs/YYYYMMDD/; failures produce a warning but do not abort the run. The Sentence Transformers model files are cached in /tmp/models/ and persist across all requests for the lifetime of the CF dyno instance, avoiding the ~10 s model load overhead on every call.

7 — API Route Reference

What this slide shows: The complete route catalog for the deployed sharepoint-rag-api FastAPI application, grouped by functional area and annotated with security guards. System: GET /health is the CF health probe — it returns app status plus the resolved site_id and drive_id confirming the Graph connection is live; it runs on a 120 s invocation timeout. Five /debug/* routes expose credential diagnostics, the HANA connection, the S3 ping, and /tmp filesystem browsing — all gated behind ENABLE_DEBUG=true. Files: GET /files fetches all root files via Graph delta and upserts metadata to BRAIN_SP_FILES without vectorizing; GET /files/versions adds version history retrieval; GET /files/all lists files from any folder path without HANA ingest; GET /files/search runs a Graph filename search; POST /download streams a file by BaseURL back to the caller and saves base64 chunks; GET|POST /rebuild reassembles a file from stored chunks. RAG — SharePoint: GET /vectorize runs the full root pipeline; GET /vectorize/folder/{path} scopes it to a subfolder; POST /vectorize accepts a caller-supplied item list; POST /vectorize/item processes a single item by ID; POST /pipeline is the most complete variant — it always fetches versions before vectorizing and saves both root data and versions JSON files. RAG — S3: POST and GET variants for prefix-scoped runs, single-object runs, and download-only (skip_ingest) runs. RAG — /tmp: POST and GET variants for folder-scoped and single-file runs against the local filesystem. Analysis: list, latest, and dated file access for HTML reports and log files stored in S3. Storage: /tmp folder/file browser with conditional delete gated by ENABLE_DESTRUCTIVE. S3: object listing, head metadata, streaming download, presigned GET and POST URL generation, single-file and bulk upload from /tmp, and object deletion. 8 — Security Controls

What this slide shows: The two environment-variable security gates that protect sensitive diagnostics and irreversible data operations, plus the separate permanent-disable mechanism for the most destructive endpoints. ENABLE_DEBUG guards five diagnostic routes that should never be exposed in an unsupervised production environment: GET /debug/destination walks through the full BTP Destination Service → XSUAA → MS Graph token chain step-by-step and prints intermediate responses (useful for diagnosing auth failures); GET /debug/db tests the HANA connection and returns host, user, schema, and DB version; GET /debug/s3 shows the credential source and bucket ping result; GET /debug/tmp and GET /debug/tmp/preview let you browse and read any file inside the CF container's /tmp filesystem — a powerful but sensitive capability. When ENABLE_DEBUG is false (the default), all five return HTTP 403 with a message indicating the flag must be set. ENABLE_DESTRUCTIVE guards seven routes that delete or wipe data: DELETE /storage/{day}/{filename} and DELETE /storage/{day} remove output files from /tmp; DELETE /s3/object/{key} and DELETE /s3/objects delete S3 objects (the bulk delete removes up to 1 000 in one call); DELETE /db/item/{item_id} removes all five BRAIN table rows for a given file; POST /db/truncate?confirm=true deletes all rows from all BRAIN tables; POST /db/drop?confirm=true drops all BRAIN tables entirely. The drop and truncate routes require an additional explicit ?confirm=true query parameter on top of the flag — two deliberate steps to prevent accidental execution. When ENABLE_DESTRUCTIVE is false, all seven return HTTP 403. Key design decisions: both flags are evaluated at request time via os.getenv(), not cached at startup — so toggling requires only a cf restart (~30 seconds) rather than a full restage or redeploy. Both are set to false in manifest.yml as explicit defaults, which means every cf push automatically resets them to off — a developer cannot accidentally leave a destructive mode on after deploying. Blocked routes remain visible in /docs so the API contract stays fully documented. To re-enable drop or truncate: cf set-env sharepoint-rag-api ENABLE_DESTRUCTIVE true → cf restart sharepoint-rag-api → call with ?confirm=true → disable again when done.

9 — s3.py — Object Store Module

What this slide shows: The design and capabilities of s3.py, the Object Store integration module used by both the vectorization pipeline and the /s3/* API routes. Credential resolution follows a priority chain evaluated at the first call: (1) VCAP_SERVICES — the CF Object Store service binding, which supplies access_key_id, secret_access_key, bucket, and a SAP BTP-specific host field; the host is normalized to an https:// endpoint URL before being passed to boto3 as endpoint_url, since SAP BTP uses its own S3-compatible endpoint rather than AWS's default. (2) s3_creds.json — a local development JSON sidecar at the project root, allowing the same codebase to run against a real S3 bucket without any VCAP_SERVICES present. (3) Standard AWS environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, S3_BUCKET) — the fallback of last resort for CI or containerized environments. Singleton client: the boto3 client is constructed once on the first request and stored in a module-level variable protected by a threading.Lock; subsequent requests reuse the same client without any initialization overhead. reset_client() can be called to force re-initialization after credential rotation without restarting the CF dyno. Auto-upload on run: _upload_run_artifacts() is called at the end of every vectorize cycle and uploads the HTML analysis report and the structured call log to S3 under runs/YYYYMMDD/; any upload failure is caught, logged as a warning, and does not affect the pipeline result — the run completes successfully regardless of S3 availability. Operations available: upload_file (path-based), upload_bytes (in-memory), upload_fileobj (streaming); download_file (to path), download_bytes (returns bytes), download_text (returns decoded string), stream_object (returns raw streaming body for large files); list_objects (with prefix and max-keys), object_exists, get_metadata (head-object); delete_object, delete_objects (bulk, up to 1 000), delete_prefix; copy_object; get_presigned_url (GET, configurable expiry), get_presigned_upload_url (POST policy for direct browser-to-S3 upload); and ping (head-bucket connectivity check used at startup and by GET /debug/s3).

10 — App Startup Sequence (lifespan)

What this slide shows: The four-step startup sequence executed once per CF dyno start via FastAPI's lifespan context manager — the code block that runs before the first request is accepted and after the last one completes. Step 1 — Validate credentials: on CF, confirms the BTP Destination Service binding is present in VCAP_SERVICES and that clientid, clientsecret, url, and uri are all set; locally, confirms TENANT_ID, CLIENT_ID, and CLIENT_SECRET are available via .env or environment variables. A missing credential raises a RuntimeError immediately, causing the CF health check to fail and CF to not route traffic to this instance — preventing the app from serving requests that would fail anyway. Step 2 — Connect to SharePoint: issues a live MS Graph API call to resolve the SharePoint site_id (from GET /sites/{hostname}:{path}) and then the document library's drive_id (from GET /sites/{site_id}/drives, selecting the first documentLibrary). This step confirms that the full auth chain (VCAP_SERVICES → XSUAA → Destination Service → MS Graph) is working end-to-end. This step is non-fatal: if Graph is temporarily unreachable (e.g. during a token service outage), the app starts, but routes that require SharePoint return HTTP 503 until the connection is available — allowing non-SharePoint endpoints like /db/query, /s3/*, and /health to continue serving normally. Step 3 — Ping S3: calls s3.ping() which performs a head-bucket request against the configured bucket. Also non-fatal — logs a warning if S3 is not configured or unreachable; /s3/* and artifact upload calls will return 503 until resolved. Step 4 — App ready: HANA table creation and schema migration are managed entirely by the HDI container at CF deploy time — the app does not run any CREATE TABLE statements at startup and does not hold the schema in memory. The embedding model is loaded lazily on the first call to any vectorize endpoint: SentenceTransformer("BAAI/bge-small-en-v1.5") is executed at that point and the model object is cached in a module-level variable for the lifetime of the dyno, keeping startup time fast and ensuring the 1 536 MB RAM budget is not consumed until the model is actually needed. The CF manifest configures: Python 3.11 buildpack, 1 536 MB memory, 4 096 MB disk, /health as the health-check endpoint with a 120 s invocation timeout, 180 s startup timeout, and three bound services: btp-catalyst-platform-destination, btp-catalyst-platform-db, and btp-catalyst-platform-objectstore.

11 — Known Gaps & Backlog

What this slide shows: Known quality and engineering gaps in the current implementation, each rated by severity and with a concrete fix described. Gap 1 — RESOLVED — Chunk size vs. model window mismatch: the original embedding model all-MiniLM-L6-v2 has a hard max_seq_length = 256 word-pieces, but _semantic_chunks() was configured with max_tokens = 512 — meaning any chunk exceeding 256 tokens would be silently truncated by the tokenizer at inference time, with the second half of the chunk contributing zero signal to the embedding. This was fixed by switching to BAAI/bge-small-en-v1.5, which has max_seq_length = 512, exactly matching the chunker window. normalize_embeddings=True is set so that all output vectors are unit-norm, making cosine similarity numerically equivalent to dot product and ensuring consistent behaviour. Vector integrity was validated end-to-end by adding a GET /db/vectors/{item_id} API endpoint that reads the raw REAL_VECTOR(384) binary from HANA, decoding the hdbcli binary format ([uint16 dims LE][uint16 padding][float32×384 LE] = 1 540 bytes) into a Python float list, then comparing element-by-element against freshly re-computed embeddings from the same chunk text — cosine similarity = 1.0 on all chunks, confirming byte-for-byte correctness between the stored vectors and a live model call. Gap 2 — MED — Character-based token approximation: _semantic_chunks() estimates chunk size as max_tokens × 4 characters, using the heuristic that one token ≈ four characters. This breaks down for content that tokenizes densely (source code, CJK characters, heavy punctuation) or sparsely (very long words). The correct fix is to count tokens using the model's own tokenizer — model.tokenizer.encode(text) — before splitting, guaranteeing chunks never exceed the sequence length limit regardless of character distribution. Gap 3 — MED — No chunk overlap: the current chunker hard-cuts at paragraph boundaries with no carry-over. When a sentence or concept straddles a chunk boundary, the first half is indexed in chunk N and the second half in chunk N+1 — but a query matching only the second half will not retrieve chunk N. Adding 10–15% overlap (approximately 26–38 tokens on a 512-token window) by carrying the last N tokens of each chunk into the start of the next would substantially improve recall for boundary-crossing concepts at modest storage cost. Gap 4 — MED — No chunk metadata: BRAIN_TEXT_CHUNKS currently stores only raw text, filename, and source. Missing columns include section heading, page number, table name (for xlsx), deliverable type, SP folder path, and version timestamp — all of which would enable filtered retrieval (e.g. "search only within Layer 3 deliverables" or "search only the latest version of each file") and provide richer citation context in LLM responses. This would require schema additions (ALTER TABLE) and changes to the extraction functions to capture structural metadata during text extraction. Gap 5 — LOW — No batched embedding: each chunk is currently embedded with a separate model.encode([chunk_text]) call inside a loop, incurring Python call overhead and preventing the model from parallelizing across chunks on the CPU's BLAS layer. Collecting all chunks for a file into a list and calling model.encode(chunks_list, batch_size=64) once would be 5–10× faster on CPU with no change to output values. Gap 6 — LOW — No vector provenance stamping: BRAIN_VECTORS stores no information about which model produced the stored embeddings. If the embedding model is ever changed (e.g. upgrading to a 768-dim model), newly written vectors would be dimensionally incompatible with existing ones, and COSINE_SIMILARITY() queries would silently return meaningless scores without any error. Adding embed_model (string) and embed_dim (integer) columns to BRAIN_VECTORS, and enforcing a model-tag match before any query, would detect this class of corruption before it reaches users.
